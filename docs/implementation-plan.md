# Implementation plan

## Goal

A REST API for Conway's Game of Life on .NET 8 (`net8.0`). A client uploads a board and asks for its next generation, the generation N steps ahead, or its final state. Uploaded boards survive application restarts and crashes. There is no authentication.

## Requirements

1. Upload a board (a 2D grid of cells) and receive a unique id.
2. Return the next generation of a stored board.
3. Return the generation N steps ahead of a stored board.
4. Return the final state of a stored board, or an error when the board does not settle within a bounded number of generations.
5. Stored boards are not lost when the application restarts or crashes.
6. Input is validated, failures produce consistent error responses, and behaviour is covered by automated tests.

## Design decisions

| # | Decision | Choice | Reason | Rejected |
|---|---|---|---|---|
| 1 | Read model | A stored board is immutable. Next, N-ahead and final are `GET` requests computed from the upload. | Reads are safe and repeatable, and no two callers can interfere. | Saving each computed generation as the board's new state (needs `POST` and optimistic concurrency). |
| 2 | Grid edges | The board keeps its uploaded rows x columns. Cells outside the grid are dead. | Responses keep the uploaded shape, work per request is bounded, and every board ends in a still life or a cycle. | Wrap-around edges; an unbounded plane. |
| 3 | Final state | The first state that repeats. Period 1 is a still life and period > 1 an oscillator; both return 200. 422 when nothing repeats within the limit. | A cycle is a settled outcome, and the response says which kind it is. | Treating oscillators as errors. |
| 4 | Database access | PostgreSQL through Npgsql with hand-written parameterized SQL. | One table and two statements; nothing is hidden behind a mapper. | An ORM; an embedded file database. |
| 5 | Schema changes | Numbered SQL scripts applied by a `migrate` command that finishes before the API starts. The API runs no DDL. | Schema change is an explicit step, and the API can run under a role without schema rights. | Migrating inside API startup. |
| 6 | Projects | `GameOfLife.Core` (no package references) and `GameOfLife.Api`. | The compiler keeps simulation code free of HTTP and database dependencies. | One project; a three-layer split. |
| 7 | HTTP style | Minimal APIs in one route group. | It is the .NET 8 `webapi` template default and fits five endpoints. | MVC controllers. |
| 8 | Cycle detection | Every generation is remembered in a dictionary keyed by board; the first repeat gives the cycle start and period exactly. | Simplest exact method. At the default limits it holds at most 1000 x 65,536 bytes = 65.5 MB of board data per request (one `bool` per cell). | Brent's algorithm: constant memory at the cost of extra simulation steps. The choice to revisit if limits are raised. |
| 9 | Cell storage | One `bool` per cell, row by row: a `bool[]` in memory and a `boolean[]` column, with `CHECK` constraints on dimensions and array length. | No code reads or writes individual bits, Npgsql maps `bool[]` to `boolean[]` directly, and the database rejects malformed rows. | Bit-packed `bytea`: 8 times smaller, but it needs bit manipulation. A JSON or text column. |
| 10 | Bad `id` or `n` | Bound as typed parameters; malformed values return 400. | ASP.NET Core routing guidance says route constraints are not for input validation. | Route constraints, which return 404. |
| 11 | Errors | Every non-2xx response is an RFC 9457 problem details document. | One error shape for clients. | Ad hoc error bodies. |
| 12 | Board ids | Random GUIDs generated by the API. | The id is known before the insert. | Database-generated ids. |
| 13 | Local configuration | A git-ignored `.env` copied from `.env.example`. | No credentials in version control. | Defaults committed in `compose.yaml`. |
| 14 | Where simulations run | Inside the request, under the hard limits and a concurrency bound: at most `MaxConcurrentSimulations` run at once, and a request beyond the bound gets 503 immediately. | One call returns the result, with no job store, worker or polling, and the bound turns extra load away instead of letting it slow every request. Durable background jobs with a job id are the next step when measured workloads outgrow a request or work must continue after the client disconnects. | Background jobs now. |

## API contract

| Method and path | Result | Success | Errors |
|---|---|---|---|
| `POST /api/v1/boards` | Stores a board | 201, `Location`, `{ "id" }` | 400, 413 |
| `GET /api/v1/boards/{id}` | The stored board (generation 0) | 200 | 400, 404 |
| `GET /api/v1/boards/{id}/next` | Generation 1 | 200 | 400, 404, 503 |
| `GET /api/v1/boards/{id}/generations/{n}` | Generation `n`, from 0 to `MaxGenerationsAhead` | 200 | 400, 404, 503 |
| `GET /api/v1/boards/{id}/final` | Final state | 200 | 400, 404, 422, 503 |
| `GET /health/live` | The process is up | 200 | |
| `GET /health/ready` | The database is reachable and migrated | 200 | 503 |

Board endpoints return 503 when the database is unavailable and 500 for an unexpected failure. `/next`, `/generations/{n}` and `/final` also return 503 "Server busy" with `Retry-After: 1` when `MaxConcurrentSimulations` requests to them are already in progress; the bound is checked before the id and `n`, so a malformed request also gets 503 while it is reached.

```json
{ "cells": [[0,1,0],[0,1,0],[0,1,0]] }
```

```json
{ "id": "…", "generation": 1, "rows": 3, "columns": 3, "cells": [[0,0,0],[1,1,1],[0,0,0]] }
```

The first block is the upload request; the second is a board response. The final-state response adds `"period"`.

Limits (configuration section `GameOfLife`, validated at startup): `MaxRows` 256, `MaxColumns` 256, `MaxGenerationsAhead` 1000, `MaxFinalStateGenerations` 1000, `MaxConcurrentSimulations` the number of processors. Request bodies are capped at 1 MB.

## Data model

`boards (id uuid primary key, row_count integer, column_count integer, cells boolean[], created_at timestamptz)`. Rows are inserted once and never updated.

`cells` layout: `row_count * column_count` booleans, row by row; the cell at (row, column) is at index `row * column_count + column` of the `bool[]`.

Applied migrations are recorded in `schema_migrations (version, name, applied_at)`.

## Solution layout

```
GameOfLife.sln
src/GameOfLife.Core/          board model, rules, final-state search (no package references)
src/GameOfLife.Api/           endpoints, Npgsql repository, SQL migrations, health checks
tests/GameOfLife.Core.Tests/  unit tests, no external dependencies
tests/GameOfLife.Api.Tests/   HTTP and PostgreSQL integration tests
scripts/                      end-to-end checks against the Compose stack
```

## Startup sequence

1. PostgreSQL reports healthy.
2. `migrate` applies pending scripts and exits 0.
3. The API starts. `/health/ready` returns 200 only when every migration is recorded.

## Testing

- Core: unit tests with no external dependencies.
- Api: integration tests over HTTP against PostgreSQL started by Testcontainers.
- End to end: scripts against the Docker Compose stack, including restart and crash survival.
- A work item is done when its tests pass, `dotnet build` reports 0 warnings (warnings are errors) and `dotnet format --verify-no-changes` exits 0.

## Tooling

.NET SDK 8.0 pinned by `global.json`; Npgsql 10.0.3; Testcontainers.PostgreSql 4.15.0; Microsoft.AspNetCore.Mvc.Testing 8.0.31; xUnit and the OpenAPI packages as scaffolded by the .NET 8 templates; PostgreSQL 16 (`postgres:16-alpine`); Docker Compose v2.

## Settled during implementation

- How ASP.NET Core 8 formats the 400 responses it generates itself: pinned by tests in the upload issue.
- Whether the `aspnet:8.0-alpine` image provides `wget` for the container health check: checked in the Compose issue.
- Simulation speed, and therefore the default limits: the measurement issue.

## Out of scope

Authentication, per-client rate limiting, request timeouts, separate database roles, board deletion or retention, caching of computed generations, a CI pipeline.
